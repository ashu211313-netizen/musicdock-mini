# 同期不良と公開状態の監査 — v2.0.1

## 統合した履歴

公開mainは831050d（v1.1.1）、ローカルは53d6c5f（v2 UI）。共通祖先b04a09bから双方に変更があり、未コミット変更はありませんでした。ローカルのv2 UI・テスト・ビルド改善を保持し、v1.1.1のparseClock、再生バー優先、古いvideo回帰ケースを統合しました。新しいリポジトリは作成していません。

## 原因と修正

旧ローカル実装は#movie_player等の最初のvideoを選び、その時刻と長さを表示していました。SPAの切り替えで旧videoが残ると、現在のタイトルと旧曲の3:25/4:18が組み合わされます。v1.1.1はバーの時計を優先する修正済みでしたが、時刻を取得できないと最初のメディアへ戻ること、同じ長さの候補を現在時刻との差で順位付けすることが残っていました。

v2.0.1は以下の契約に変更しています。

- 表示時計の唯一の基準は実ページの.time-info。バーの値がないときは「—:—」で、メディアの古い時計へ戻りません。
- #progress-barのaria値がある場合は、時計と整合するか確認します。
- #movie_player配下で、時刻・長さが1.5秒以内に一致する一意の候補だけを採用。hidden/inert/広告/エラー/未ロードを除外。
- 候補が複数ある場合、近さで勝手に選びません。シーク・音量・ミュートを無効化。
- 600msの安定期間と、曲が変わった際のsource更新またはloadstart/emptied/loadedmetadataイベントを確認。
- ドラッグ開始時のbinding tokenを保持。完了前に曲やリソースが変われば、シークを拒否。
- タイトル切り替えに音声更新が追い付いていない間は、以前の曲の数字を新しいタイトルに表示しません。
- DOMのyt-icon-button内側のbuttonを使用し、親子両方のdisabled/inert状態を尊重。

これにより、表示値だけを補正せず、操作対象の選択とライフサイクル自体を修正しています。DOM上の時刻・メタデータ・イベントによる照合であり、YouTubeの内部安定APIや暗号的な楽曲ID対応を保証するものではありません。証拠が不足する場合は機能を安全側へ制限します。

## 実ページで観測したDOM（2026-10-24）

組み込みブラウザから実際のmusic.youtube.comを開き、ログイン情報を取得せず、以下を読み取りました。

- ytmusic-player-bar .time-info / #progress-bar / .title / .byline
- .play-pause-buttonはyt-icon-buttonで、内部に実buttonとaria-labelがある
- アーティストのhrefはchannel/...、アルバムはbrowse/...、年は別span
- 通常曲「Yes! 東京」: バー0:57 / 3:41、video57.642秒 / 220秒。長さに1秒の丸め差。
- 広告中: タイトルは空、bylineは「動画は広告の後に再生されます」、バー0:00 / 0:31に対してvideoは約24秒 / 30.061秒。
- 別曲への遷移後もバーとvideoの時計を読み取り、一時停止して確認を終了。

実ページのDOMと時計の観測は実施しましたが、そのブラウザへ開発中拡張機能を読み込んだ統合試験はしていません。ユーザーから報告されたAll I Needの瞬間のDOMは取得できないため、その実機での直接再現完了とは主張しません。

## 回帰・UI検証

単体30件。報告された205秒/258秒の古いvideo、同じ長さで違う時刻の候補、複数候補、source更新なしのタイトル変更、ドラッグ中の曲変更、SPA要素交換、バー消失、disabled、丸め差を検証。

ブラウザでは実拡張機能をChromium for Testingへ読み込み、実Document PiPを開いて操作。別途、製品レンダラーを用いて長文のCJK/英数字、中央ボタン、音量、エラー、370×240 / 320×220 / 270×195 / 240×170 / 220×160 / 520×280を検証します。

ネイティブPiPに1×1への縮小を要求したところ、このヘッドレス環境では実内容244×57が得られました。通常レイアウトは収まらないため、高さ100以下に専用の2行コンパクト配置を追加。曲情報、時刻、シーク、前/再生/次/音量を残し、冗長な独自ヘッダーは省略します。標準タイトルバーの閉じる・元タブ復帰はブラウザに委ね、削除しません。測定値はdocs/browser-minimum.jsonを参照。Windows上での手動縮小の最小サイズや最前面挙動は別途確認が必要です。

## 公開方法

Windows側ghはこの実行環境では認証無効と報告するため、正式なGitHub連携のリポジトリ書き込みAPIを使用します。既存mainを親に通常のコミットを追加し、期待SHA付きのfast-forward更新のみを行います。資格情報の抽出・複製・ブラウザ権限の回避は行いません。

既存Pagesワークフローで型・単体・ブラウザ・ZIPを検証して公開。その成功を受けて既存Releaseワークフローが公式GITHUB_TOKENを使用し、Pagesで検証した同一ZIPをReleaseへ登録します。新たな外部サービスや永続的な認証トークンを追加しません。

最終ローカル結果: 型チェック成功、単体30件、ブラウザ5件成功。ネイティブ最小244×57でscrollWidth=244、scrollHeight=57、再生ボタンが操作可能であることを確認。画面写真は架空のテスト曲です。
